## What this project is

**GreenOps** — a submission for problem statement **IPS12: Intelligent Data
Center Resource Optimization and Sustainability Management Platform**.

**The problem it solves:** Data centers waste energy, cost, carbon, and water
because operators can see *what's happening* (CPU%, PUE) but have no system
telling them *what to do about it*. Existing monitoring tools (Prometheus,
DCIM, BMS) report numbers; nothing sits on top of them to decide what's
wasteful, quantify the impact of fixing it, and recommend an action.

**What GreenOps is:** A resource intelligence and sustainability
decision-support layer that sits *above* existing monitoring tools (it does
not replace them). It observes four telemetry domains, detects waste,
estimates the energy/cost/carbon/water impact of fixing it, and (in the
still-unbuilt Phase 2) ranks and recommends actions — always with a human
approving before anything happens. It is explicitly **not** an autoscaler and
does not control infrastructure automatically.

**The five-word mental model:** `OBSERVE → ANALYZE → PREDICT → EVALUATE → RECOMMEND`

## Current status: Phase 1 complete, Phase 2 not started

The project is explicitly split into two phases. **Only Phase 1 is built.**
Do not imply Phase 2 features exist in code, docs, or UI copy unless you are
the one building them.

### Phase 1 — Observability & Resource Intelligence Foundation (BUILT)
- 4 telemetry domains ingested: server, power, cooling, storage
- FastAPI + SQLAlchemy + SQLite (swappable to Postgres via one env var)
- PUE, WUE, energy, cost, carbon computed live via plain formulas — no ML
- Rule-based flags: idle servers (per-server-type threshold), stale/duplicate/
  over-provisioned storage
- Two ML models trained on a **real** dataset (not synthetic): CPU estimation
  and power estimation, comparing Linear Regression / Random Forest / XGBoost
- React dashboard (Overview, Servers, Server Detail, Storage, Analytics,
  Model Evaluation) with real visual components (ring gauges, capacity bars,
  sparklines) — not just numbers in boxes

### Phase 2 — Prediction, Impact & Recommendation (NOT BUILT — design only)
Everything below has been discussed and designed in detail but has **zero
code**. See `docs/ROADMAP.md` for the full spec before building any of it.
- Workload forecasting (near-future demand prediction)
- What-if simulation engine (test a hypothetical consolidation before
  recommending it)
- Sustainability impact ranking + weighted recommendation engine
- ESG report export, Preferences page (org-configurable priority weights)
- Criticality/SLA/redundancy tagging (a real, named gap — see
  `docs/DECISIONS.md` → "Criticality cannot be inferred from telemetry")

**If asked to "add the recommendation engine" or similar, treat it as new
Phase 2 work, not a bug fix or a small addition.** Re-read `docs/ROADMAP.md`
first.

## Non-negotiable conventions (things that were deliberately decided — don't "fix" these)

1. **Data provenance must stay honest.** Live telemetry is simulated (no real
   data-center access). The ML models train on a real historical dataset —
   `green_ai_datacenter.csv` — not on the simulators' output. Never blur this
   distinction in code comments, docs, or UI copy. See `docs/DECISIONS.md`.

2. **Per-server-type idle thresholds, not a flat number.** `idle_cpu_threshold`
   is computed per `server_type` from the real dataset (`mean − 1.5×std`,
   clamped to [5, 35]) via `compute_thresholds.py`. Never reintroduce a single
   global threshold constant.

3. **CPU model excludes `cpu_utilization` from its own inputs** (target
   leakage). The **power model includes it** as an input, because CPU is not
   the target there. Keep this distinction if you touch `train_model.py`.

4. **Model selection rule:** lowest MAE wins, UNLESS a more complex model
   (Random Forest / XGBoost) beats Linear Regression by less than 5% relative
   MAE — in which case keep Linear Regression for explainability. See
   `select_winner()` in `train_model.py`.

5. **WUE and carbon figures are estimates, not measurements.** They use
   published industry-average constants (`WUE_FACTORS` in `rules_engine.py`,
   a placeholder carbon-intensity constant in `main.py`). Never present these
   as real meter readings in UI copy or docs.

6. **PUE is the only "physical" ratio computed from two directly-simulated
   numbers** (`facility_power_kw ÷ it_power_kw`). Don't conflate its
   trustworthiness with WUE's.

7. **The frontend is React (Vite), not the old static HTML file.**
   `frontend-static-legacy/` is kept only for reference — do not build new
   features there.

8. **`npm run build` and a Playwright screenshot pass caught real bugs before**
   (broken flex layout, a manufactured "PUE = 72%" display bug, invisible
   text on dark backgrounds). If a headless Chromium is available in the
   environment (check `/opt/pw-browsers/` or run
   `npx playwright install chromium`), always screenshot new UI work before
   calling it done — don't just trust that a clean build means it looks right.

## How to run it

```bash
# Backend
cd backend
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
python -m app.compute_thresholds     # one-time: derive per-type thresholds from the dataset
python -m app.train_model            # one-time: train CPU + power models (~15s)
uvicorn app.main:app --reload        # API at http://localhost:8000

# Simulators (each in its own terminal)
cd simulators
python server_monitor.py
python power_monitor.py
python cooling_monitor.py
python storage_monitor.py

# Frontend
cd frontend
npm install
npm run dev                          # UI at http://localhost:5173
```

Swap SQLite for Postgres with `export DATABASE_URL="postgresql://..."` — no
code changes needed, `database.py` reads it automatically.

## Tone/framing to preserve if writing docs, comments, or UI copy

This project has been deliberately built and described with **honesty about
its own limitations** — simulated vs. real data, estimated vs. measured
metrics, validation-layer vs. recommendation-engine models. Don't let new
code or copy overclaim what's built. When in doubt, state the limitation
plainly rather than implying more sophistication than exists.
