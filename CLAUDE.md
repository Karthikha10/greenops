## What this project is

**GreenOps** — a submission for problem statement **IPS12: Intelligent Data
Center Resource Optimization and Sustainability Management Platform**.

**Problem it solves:** data centers can see *what's happening* (CPU%, PUE)
but nothing tells them *what to do about it*. GreenOps is a resource
intelligence and sustainability decision-support layer that sits **above**
existing monitoring tools (doesn't replace them). It observes four telemetry
domains, detects waste with explainable rules, forecasts near-term demand,
simulates and ranks consolidation/storage recommendations, and estimates
their energy/cost/carbon/water impact — with a human always approving before
anything happens. **Not** an autoscaler; never controls infrastructure
automatically, and never will.

**Mental model:** `OBSERVE → ANALYZE → PREDICT → EVALUATE → RECOMMEND`

**Database: Postgres, already connected.** `backend/.env` holds
`DATABASE_URL=postgresql://greenops_user:green123@localhost:5432/greenops_db`
— this is real, working, tested end to end. Two things to never do again:
don't touch `greenops_review1_db` (a sibling database, unrelated, leave it
alone) and don't attempt to reset the Postgres superuser's password — that
whole path was a dead end last time (no admin access available). If Postgres
ever needs re-pointing, `greenops_user` already owns `greenops_db` and has
full DDL rights on it, so no admin access is ever needed for anything to do
with this project's own tables. Start the backend with
`uvicorn app.main:app --reload --env-file .env` (from `backend/`) so the
`.env` file is actually picked up.

**Status: Phase 1 and most of Phase 2 are built.** Forecasting, real what-if
simulation, weighted ranking, operator decisions (including snooze), and ESG
export all exist and run end to end — see "Phase 2 — what's actually built"
below. **Explicitly not built: criticality/SLA gating** — the roadmap's item
5 remains a deliberate, discussed, unbuilt gap (see `docs/DECISIONS.md` →
"Criticality cannot be inferred from telemetry"). Nothing here should be
read as gating a consolidation recommendation on whether a server is
critical — it isn't, on purpose, until that's built.

## Architecture / data flow

```
4 simulators (server/power/cooling/storage), each posting JSON every 15-30s
        ↓ HTTP POST
    FastAPI (Pydantic validation)
        ↓
    SQLAlchemy → SQLite
        ↓
  ┌─────────────┬──────────────┐
  ↓             ↓              ↓
Rule engine   Analytics     ML models
(no ML)       (aggregates)  (CPU + power estimation)
  ↓             ↓              ↓
        React dashboard (6 pages, listed above)
```

**Two pipelines never touch each other:** live telemetry is 100% simulated
(no real data-center access available) — the ML models train on a real,
static, 10,000-row Kaggle dataset (`green_ai_datacenter.csv`), never on
simulator output. They're connected only by matching schema (same column
names/meanings). State this distinction plainly whenever the project is
described — never imply the dashboard shows "real" readings, and never imply
the ML models learned from the live simulators.

## The four telemetry domains — what each provides, what's derived

| Domain | Simulator | Fields posted | Feeds into |
|---|---|---|---|
| Server | `server_monitor.py` | `cpu_utilization`, `memory_utilization`, `network_throughput_gbps`, `workload_intensity` | Idle-server flag (6h avg CPU vs. per-type threshold), CPU/power ML model inputs, Servers page, Analytics CPU chart |
| Power | `power_monitor.py` | `it_power_kw`, `facility_power_kw` | **PUE** = `facility ÷ it`; feeds energy → cost → carbon → WUE |
| Cooling | `cooling_monitor.py` | `inlet_temperature_c`, `cooling_efficiency`, `cooling_type` | WUE factor lookup; also two ML model input features |
| Storage | `storage_monitor.py` | `total_storage_gb`, `used_storage_gb`, `duplicate_data_gb`, `last_accessed_days_ago` | stale / duplicate / over-provisioned flags |

## Rule-based detection — no ML, by design (`rules_engine.py`)

Detection is deliberately rule-based, not ML: rules are explainable and need
no training data to exist on day one. Four checks, all simple threshold
logic a human could verify by hand:

| Flag | Rule |
|---|---|
| `idle_server` | avg CPU over **last 6h** < that server type's dataset-derived threshold |
| `stale_data` | `last_accessed_days_ago` > 90 |
| `duplicate_data` | `duplicate_data_gb / total_storage_gb` > 20% |
| `overprovisioned` | `used_storage_gb / total_storage_gb` < 30% |

**Per-server-type idle thresholds** (`compute_thresholds.py`, run once against
the real dataset): `threshold = mean_cpu(type) − 1.5×std_cpu(type)`, clamped
to `[5, 35]`, plus `severity_weight = avg_power_kw(type) / min(avg_power_kw across types)`.

Real computed values:

| Type | Threshold | Severity weight |
|---|---|---|
| GPU | 16.9% | 1.66x |
| Compute | 17.3% | 1.22x |
| Storage | 16.8% | 1.06x |
| Edge | 18.9% | 1.0x (baseline) |

**Never reintroduce a flat global threshold.** Unrecognized `server_type` →
`_default` fallback (20%, weight 1.0) — intentional, not a gap to "complete."

The `/servers` list endpoint's status badge must use the **same 6h-windowed
average** as this rule (was a real bug: it used to compare instantaneous CPU
against an unbounded all-time average, which could disagree with the actual
flag — fixed).

## Sustainability metrics — computed vs. estimated

| Metric | Formula | Trust level |
|---|---|---|
| **PUE** | `facility_power_kw ÷ it_power_kw` | Real ratio of two directly-simulated numbers — the one number here that's genuinely "physical" |
| **Energy (kWh)** | True time integration: for each server, sum `power_kw × actual_hours_elapsed` between consecutive readings (left Riemann sum over real timestamps), skipping gaps > 5 min (telemetry downtime isn't counted as sustained draw) — `rules_engine.compute_energy_kwh()` | Correct as of this session's fix — previously assumed every reading = 1 minute, which overcounted ~4x since simulators actually post every 15s |
| **Cost** | `energy_kwh × TARIFF_PER_KWH` (₹8.0, hardcoded placeholder) | Estimate |
| **Carbon** | `energy_kwh × CARBON_INTENSITY_KG_PER_KWH` (0.5, hardcoded placeholder) | Estimate |
| **Total water (L)** | `total_water_l` = cumulative `energy_kwh × WUE_FACTOR[cooling_type]` per server, summed — since telemetry began, weighted by each server's own cooling type (Air 0.3, Evaporative 1.8, Liquid 0.9 L/kWh) | Estimate. A running total, not a rate — expected to keep climbing the longer the system runs |
| **WUE (L/kWh)** | `wue_l_per_kwh` = the *same* per-server weighted water calc, but both water and energy computed only over the last `WUE_WINDOW_HOURS` (default 1h) via `rules_engine.compute_wue_rate()` | Estimate. A real ratio in shape (should stabilize at steady state), but still built on placeholder factors, not a meter |

**Never derive water straight from CPU.** The only defensible causal chain is
`CPU/workload → power → energy → × WUE factor → water`. In production, cost/
carbon/WUE would be replaced by a real tariff, a live grid carbon-intensity
API (WattTime, ElectricityMaps), and a real facility water meter — never
presented as measured today.

**Don't collapse "total water" and "WUE" back into one number.** They answer
different questions — "how much water has this run used so far" vs. "how
much water per unit of energy, right now" — and conflating them is exactly
the bug that was fixed (see "Bugs found and fixed" below). Also don't compute
the weighted water total using a single "most recently posted" cooling
reading for the whole facility — servers here use three different cooling
types with WUE factors up to 6x apart, so that picks an almost arbitrary
factor depending on refresh timing. Always weight per-server.

## The two ML models (`train_model.py`)

Both trained on `green_ai_datacenter.csv` (10,000 rows, 4 `server_type`
categories: Compute/Edge/GPU/Storage; 3,990 missing `datacenter_region`
values, imputed via `SimpleImputer(strategy="most_frequent")` inside the
pipeline so live inference replays the same logic).

**Preprocessing** (`ColumnTransformer`): numeric → `StandardScaler()`;
categorical → impute → `OneHotEncoder(handle_unknown="ignore", drop="first")`.
`drop="first"` matters: without it, one-hot-encoding every category plus an
intercept creates a perfectly collinear design matrix — this caused a real
bug where `LinearRegression`'s coefficients were numerically unstable (in the
trillions), invisible in offline test metrics but catastrophic on live
single-row predictions. Fixed and retrained; offline metrics unchanged
(collinearity affects numerical stability, not fit quality).

| | CPU model | Power model |
|---|---|---|
| Target | `cpu_utilization` | `power_consumption_kw_rescaled` (see rescale note below) |
| Numeric inputs | workload_intensity, memory_utilization, network_throughput_gbps, inlet_temperature_c, cooling_efficiency, pue | same six **+ `cpu_utilization`** |
| Categorical inputs | server_type, cooling_type, datacenter_region, time_of_day | same |
| Role | Validation layer — proves the feature set explains resource behavior. **Not** the recommendation engine. | Primary basis for What-If's energy estimate — see "Phase 2 — what's actually built" → `recommendations.py` below for what changed and why |
| Real MAE / RMSE / R² | 4.51 / 7.67 / 0.845 | 0.211 / 0.330 / 0.422 (rescaled kW — see below) |

CPU model deliberately excludes its own target (leakage); power model
includes CPU as input (legitimate — CPU isn't the target there). **Don't
"fix" this into symmetry — the asymmetry is correct.**

**Power model target is rescaled before training** (`rescale_power_target()`
in `train_model.py`) — the Kaggle dataset's `power_consumption_kw` runs
28-233kW (real data-center scale); live telemetry runs ~1.2-4.5kW. A linear
min-max transform maps the training target into
`LIVE_IT_POWER_MIN_KW`..`LIVE_IT_POWER_MAX_KW` before training, so the
model's output is directly usable against live numbers. This is a pure unit
change, not a different fit — confirmed by R² being numerically identical
(0.422) before and after the rescale was introduced. The MAE/RMSE above are
now in rescaled kW, not the dataset's original scale — don't compare them
against an older copy of this doc that shows 13.14/20.55.

**Candidates & hyperparameters** (all trained on the same 80/20 split,
`random_state=42`):
```python
LinearRegression()
RandomForestRegressor(n_estimators=200, random_state=42, n_jobs=-1)
XGBRegressor(n_estimators=200, max_depth=5, learning_rate=0.1, random_state=42)
```

**Selection rule** (`select_winner()`): lowest MAE wins by default, but RF/
XGBoost must beat Linear Regression by **≥5% relative MAE** to be chosen over
it — otherwise keep the simpler model. On this dataset Linear Regression wins
both targets; neither RF nor XGBoost cleared the bar.

**Inference** (`/servers/{id}/prediction` in `main.py`): builds a one-row
DataFrame from the server's latest live telemetry; `time_of_day` is currently
hardcoded to `"Peak"` (known simplification, not wired to real time yet).
**Expect live prediction errors to run higher than the reported MAE** — the
model trains on real historical relationships, but live data comes from
simulators using their own simplified generation formulas (e.g.
`server_monitor.py`'s `cpu = workload_intensity × 100 + noise`). This is a
genuine train/inference distribution shift, not a bug — the Server Detail
page shows measured-vs-predicted side by side specifically so this gap stays
visible instead of hidden.

## Frontend — current state

React + Vite + `react-router-dom` + `recharts`. No separate visual-primitives
file — each page inlines its own metric cards / tables / charts using shared
CSS classes from `index.css` (`.metric-card`, `.badge`, `.card`,
`.data-table`, `.chart-grid`, etc.).

**Design language (current, deliberate):**
- Every metric card states a colored verdict pill (e.g. "above ideal",
  "healthy load") **plus a plain-English relationship sentence** — not a
  static caption, not a gauge/ring/progress-bar. Gauges and capacity bars
  were explicitly rejected as confusing without adding real information —
  don't reintroduce them.
- Tables that were really a small categorical comparison (idle threshold by
  server type, MAE/RMSE/R² by model, storage waste by category) were
  converted to `recharts` bar charts. Per-row/per-server listings stay as
  tables — that's appropriate, not something to convert.
- Line charts use gradient-filled `AreaChart` (see `cpuFill` pattern in
  `Analytics.jsx` / `ServerDetail.jsx`), not plain lines.
- Wording: avoid "fleet" — use "servers" / "data center" / "all servers".
  Normal data-center terminology, not jargon.
- Every server ID in every table links to `/servers/:id` (Overview's table
  didn't used to — fixed).
- **Table borders are chosen per-table, not global.** Plain `.data-table`
  (row hairlines only) is for row-by-row scanning (Reports' decision log,
  ServerDetail's flag list). `.data-table.gridded` (full vertical + horizontal
  grid lines, rounded outer corners) is for tables meant to be scanned
  *column-by-column* too — currently only the Recommendations list. Don't
  add `gridded` everywhere by default; it's a deliberate choice for that one
  table, made after explicit feedback ("clear vertical and horizontal lines
  i want").
- **Recommendations is list → detail, not everything inline.** `/recommendations`
  is a compact triage table (Server / Action / Priority / Target-status /
  Score, no "Why" column — that belongs on the detail page, not the list);
  clicking a row goes to `/recommendations/:id` (`RecommendationDetail.jsx`),
  which shows the full explanation, the ranked candidate-targets table, the
  impact numbers, and the decision buttons. This replaced an earlier
  version that tried to show everything as expanded inline cards and was
  reported as "atmost blank and can't comprehend properly" — don't revert
  to that shape.

**Known-good reference for the current style:** `Overview.jsx` and
`Servers.jsx`.

## Phase 2 — what's actually built

Everything below is real, tested end to end against live telemetry — not
design notes. **Criticality/SLA gating is the one deliberate exception, not
built.**

**`forecasting.py` / `train_workload_forecast.py`** — near-term (15/30/60min)
CPU forecast, gated to only run for servers currently idle/underutilized by
the same 6h rule the flags use. Trains a lagged-feature model (5/10/15/20min
CPU lags + hour-of-day) from real timestamped telemetry once ≥30 samples
exist; falls back to transparent trend extrapolation until then, and says so
(`"model_ready": false`) rather than pretending. Endpoint:
`GET /servers/{id}/forecast`. **Only `horizon_minutes=15` actually uses the
trained model** — 30/60 (both offered in the Server Detail dropdown) always
fall back to `trend_forecast()` extrapolation, silently. Not a bug, just a
real limitation worth knowing about: `FORECAST_HORIZON_MINUTES = 15` is the
only horizon the model was trained for.

**Target-candidate forecasting** (`forecasting.forecast_candidate_server()`)
— a second, separate forecasting path with the mirror-image eligibility
rule from the one above: `forecast_server()` only runs on already-idle
servers ("will this idle server stay idle"); this one runs on *any*
registered server with enough telemetry, specifically because a
consolidation TARGET is by definition not idle and could never pass the
other function's gate. **This does not require a separate trained model**
— `build_feature_rows()` was never restricted to idle servers in the first
place, so the exact same CPU model already generalizes to busy servers; the
"idle only" restriction was purely `forecast_server()`'s own inference-time
rule, not a training-data limitation. What *is* new: a genuine **memory**
forecast model (`workload_forecast_memory_model.joblib` /
`forecast_memory_metrics.json`), trained identically to the CPU one (same
features, same selection rule) but a separate file so each target's own
MAE/RMSE/R² stays independently visible — the CPU model alone was never
enough here, since the safety check needs both dimensions. Both are trained
together in one `train_workload_forecast.py` run via `_train_one_target()`.
Used by `_rank_consolidation_candidates()` below — not used anywhere else.

**`recommendations.py`** — converts active flags into `Recommendation` rows
(`idle_server`→consolidate, `stale_data`→archive, `duplicate_data`→dedupe,
`overprovisioned`→rightsize). For consolidation specifically, `GET
/recommendations/{id}/what-if` (and `GET /recommendations/{id}`) runs a
**real simulation**, not a source-only estimate:
1. `_rank_consolidation_candidates()` finds every same-type server that
   isn't itself idle-flagged, computes `post_move_cpu/memory =
   target.current + source.current × 0.9` (overhead factor) for **all** of
   them, and returns the full ranked list (safe-first, then most headroom
   left) — not just a single winner. The what-if response's `candidates`
   array (top 5) exposes this whole ranking, which is what
   `RecommendationDetail.jsx` renders as a table so an operator can see what
   else was considered, not just take the pick on faith.
2. Both CPU and memory must stay under 75% for a candidate to count as safe
   — checked **twice**: once against the candidate's current snapshot
   (`safe_now`), and once against its own near-term forecast via
   `forecasting.forecast_candidate_server()` (`safe_forecast` — the
   candidate's own predicted CPU/memory 15 minutes out, independent of this
   move, plus the same source contribution). A candidate only counts as
   `safe` when both agree. **This closes a real gap**: a target can look
   fine right now and still be a bad pick if it's about to get busy on its
   own — the snapshot check alone has no way to see that. When a forecast
   isn't available yet (not enough history for that specific candidate —
   this can flip per-request on a live system near a data gap), the
   forecast check is skipped rather than treated as a failure; missing data
   shouldn't block a recommendation the snapshot check already approved.
   Exposed per-candidate as `safe_now`/`safe_forecast`/`forecast_available`/
   `forecast_predicted_cpu`/`forecast_predicted_memory`, and
   `RecommendationDetail.jsx` shows a distinct "Risky soon" badge for a
   candidate that passed the current check but failed the forecast one.
3. The top-ranked **safe** candidate is the one actually used for the impact
   estimate below it; if none qualify, `"safe": false` with a stated reason
   — never silently approved.
4. Energy/cost/carbon/water savings prefer the **trained power model's
   prediction** for the target's full post-move profile (CPU, memory,
   network, cooling) — scaled from predicted IT power to facility power by
   the target's current PUE. This is the primary basis for `energy_after`
   whenever `power_model` and the target's cooling telemetry are both
   available. It falls back to the older, simpler formula (**target's own
   current live facility power scaled by its post-move CPU ratio**) only
   when either is missing. See "The two ML models" above for the rescale
   mechanics.

   **This was NOT always wired in — read this if the formula looks wrong.**
   For most of Phase 2's life, the power model's raw output was deliberately
   *never* used for the dollar figure, only surfaced as
   `model_predicted_target_it_power_kw` for transparency, because two
   separate problems made using it dishonest:
   1. **Scale mismatch** — the model was trained on the Kaggle dataset's own
      power range (tens-to-hundreds of kW); live telemetry runs single-digit
      kW. Fixed in `train_model.py` via `rescale_power_target()` — a linear
      min-max transform of the training target down to
      `LIVE_IT_POWER_MIN_KW`..`LIVE_IT_POWER_MAX_KW` before training. Same
      learned relationships, different output units — confirmed by R²
      staying identical (0.422) before and after rescaling.
   2. **The live simulator had zero causal relationship between load and
      power to begin with** — `simulators/power_monitor.py` generated
      `it_power_kw` via pure `random.uniform(1.5, 4.5)`, completely
      independent of CPU/memory. Applying a real-world-trained model to
      that would have produced a number that *looked* ML-validated while
      being no more meaningful than the noise it was applied to — worse
      than the honest CPU-ratio formula, not better. **Fixed by making
      power_monitor.py itself respond to real load**: it now fetches each
      server's current CPU/memory from `GET /servers` before generating a
      reading, and computes `it_power = BASELINE_IT_KW + variable component
      weighted 85% CPU / 15% memory + noise`, landing in the same overall
      range (~1.2–4.5kW) the simulator always used — S6's old hardcoded
      "always low power" special case was removed as a result; it's simply
      low now because its CPU is genuinely low, the same reason a real idle
      server draws less power. **Do not revert this to random generation.**

   **Even after both fixes, this remains an estimate, not a measurement**
   — the model's learned relationship (from real Kaggle servers) and
   `power_monitor.py`'s hand-written formula are two independently-built
   approximations of the same idea. They now agree on direction and scale,
   but won't numerically match exactly for a given CPU/memory input — the
   same "train/inference distribution shift" already documented for the
   CPU/power validation models. `calculate_what_if()`'s assumptions list
   says this explicitly every time the model is used. Don't let this
   get framed as "solved" or "now accurate" — it's "now legitimate to use,"
   which is a different, more honest claim.

   **A landmine for a future retraining effort, noted here so it isn't
   hit blind:** telemetry collected *before* the power_monitor.py fix has
   power generated the old random way (zero correlation). If a future
   session ever pursues training the power model directly on accumulated
   live data instead of the Kaggle CSV (previously called "Option 2" —
   not viable yet, only ~2 hours of live history exists as of this
   writing), that pre-fix data **must be excluded** from that training set,
   or it would silently corrupt it by mixing two different data-generating
   regimes. Check `power_monitor.py`'s git history / a timestamp cutoff
   before trusting any bulk export of `power_telemetry` for that purpose.

**Recommendations UI is list → detail, not one long page of expanded
cards.** `/recommendations` is a compact table (server, action, priority,
target/status, score) — click a row to go to `/recommendations/:id`, which
fetches `GET /recommendations/{id}` (recommendation metadata + full
`impact`, including `candidates`) and shows the full explanation, the ranked
candidate table, the impact numbers, and the accept/snooze/dismiss buttons.
Don't put the full detail back inline in the list rows — that was tried and
was "atmost blank and can't comprehend properly" per direct feedback; the
list's job is triage, the detail page's job is the decision.

**Ranking** (`rank_recommendations()`) — pending recommendations are scored
as `Σ(weight × normalized_impact) − risk_weight × risk`, normalized against
the max of each dimension in the current pending batch (so kWh/₹/kg/L don't
silently dominate each other by raw magnitude). Weights live in a single-row
`Preferences` table, editable via `GET`/`PUT /preferences` and the
Preferences page — changing them re-ranks immediately, nothing retrains.
Risk for consolidation = `max(post_move_cpu, post_move_memory) / 75`; for
storage-only actions (no target, no power effect) it's a fixed `0.1`.

**Operator decisions** (`record_operator_action()`) — `consolidate` /
`rightsize` (also the generic accept verb for archive/dedupe) / `snooze` /
`do_nothing`. Snooze sets `snoozed_until`; `sync_recommendations()` reopens
it as pending automatically once that passes, rather than losing the flag.
Every decision snapshots the what-if impact **at decision time** into
`OperatorAction` — the ESG report reads that snapshot, not a live
recalculation, so the log reflects what the operator actually saw.

**ESG report** (`GET /reports/esg`, `/reports/esg/export` for CSV) —
aggregates `OperatorAction` snapshots over a date range: decision counts
(accepted/snoozed/rejected) and summed estimated impact. Explicitly labeled
as a **decision log, not a verified savings report** — there's no mechanism
anywhere in this system to confirm a consolidation was actually carried out
or to re-measure its real effect afterward. Don't let UI copy imply
otherwise.

**Duplicate-event ignore** — `_is_duplicate_reading()` in `main.py`: the same
server posting identical field values again within 2 seconds is treated as a
retried delivery and silently ignored (`"status": "duplicate_ignored"`), not
double-counted into any aggregate.

## Bugs found and fixed this session (context for future debugging)

1. **Idle badge / rule mismatch** — `/servers` list endpoint computed the
   Healthy/Underutilized badge from instantaneous CPU vs. an unbounded
   all-time average; the actual `idle_server` flag rule uses a 6h *windowed*
   average. Could disagree. Fixed to share the same window and threshold
   source.
2. **Dummy-variable trap in `train_model.py`** — see ML section above.
   `LinearRegression` coefficients were numerically unstable; a live
   prediction could return something like `1.9 trillion %`. Fixed with
   `OneHotEncoder(drop="first")`, retrained.
3. **Energy formula overcounted ~4x** — assumed every telemetry reading
   represented a fixed 1-minute interval; simulators actually post every 15s.
   Replaced with true timestamp-based integration (`compute_energy_kwh()`).
4. **WUE used one arbitrary cooling type for the whole facility** — picked
   whichever single `CoolingTelemetry` row was posted most recently across
   *all* servers, applied that one cooling type's factor to total facility
   energy. With 3 cooling types in play (factors up to 6x apart), the number
   could swing 6x depending purely on refresh timing. Fixed with
   `compute_wue_liters_weighted()` — per-server energy × that server's own
   cooling type, summed.
5. **WUE was a cumulative total mislabeled as a rate** — `estimated_water_l`
   was energy-since-telemetry-began × factor, so it only ever grew and never
   stabilized, despite the UI calling it "WUE." Real WUE is L/kWh, a ratio.
   Split into `total_water_l` (cumulative, honestly labeled as such) and
   `wue_l_per_kwh` (windowed rate, `compute_wue_rate()`) — see
   `docs/DECISIONS.md` → "WUE was mislabeled..." for the full writeup.
6. **`total_storage_gb` / `stale_storage_gb` were inflated by a join/aggregation
   fan-out** — both summed a telemetry column (`total_storage_gb`,
   `used_storage_gb`) across *every historical row*, not just each server's
   latest reading. Since storage capacity is reposted unchanged every ~30s,
   this multiplied the real total (5,000 GB across S1-S5) by however many
   readings had accumulated — confirmed live at 1,440,000 GB (288x) and
   climbing. Fixed with `_latest_row_per_server()` in `main.py` — a
   latest-timestamp-per-server_id subquery, then aggregate over just those
   rows. Same root cause as the energy/WUE bugs: summing across accumulated
   history instead of taking a current snapshot.
7. **Flags never resolved** — nothing in the codebase ever set
   `Flag.resolved = 1`; a server that stopped being idle (or stopped having
   stale/duplicate/over-provisioned storage) kept its flag forever, so
   `active_flags` only ever grew. Fixed with `_resolve_flag()` in
   `rules_engine.py`, called from the `else` branch of every rule check —
   same cadence and same code path as flag creation, so a flag clears exactly
   as promptly as it's raised.
8. **Overview.jsx compared the instant CPU reading, not the 6h average, in
   its inline threshold text** — same class of bug as #1, but in the
   frontend: the Healthy/Underutilized badge used `avg_cpu` (6h window,
   matching the actual rule) while the text next to it ("— above/below its
   X% idle line") compared the instant `cpu` reading, so they could disagree
   on the same row. `Servers.jsx` never had this bug. Fixed to use
   `avg_cpu` in both places, and the text now says "6h avg X%" explicitly so
   it can't be mistaken for describing the instant reading.

**A later session found files had been edited on disk by an unknown external
source between sessions (not by the assistant) — several previously-fixed
bugs above had been reintroduced, plus new ones. All re-fixed and
re-verified live:**

9. **`idle_server` reintroduced on ServerDetail.jsx** — the "Underutilized"
   verdict was recomputed client-side as `avg_cpu < threshold OR instant_cpu
   < threshold`, reintroducing the exact instant-vs-6h-average mismatch from
   bug #1/#8, this time flagging servers whose *momentary* CPU dipped low
   even though their 6h average (and the real backend flag) said healthy.
   Fixed to read `isIdleFlagged` purely from whether an actual `idle_server`
   Flag row exists for that server — never re-derive the rule client-side.
10. **Hardcoded WUE factor on ServerDetail.jsx** — water-per-server math used
    a single constant (1.8, the Evaporative factor) regardless of that
    server's actual `cooling_type`, so Air- and Liquid-cooled servers showed
    inflated water numbers. Fixed with a client-side `WUE_FACTORS = { Air:
    0.3, Evaporative: 1.8, Liquid: 0.9 }` map keyed off the real field,
    matching `rules_engine.WUE_FACTORS` on the backend.
11. **Fabricated power history chart** — ServerDetail.jsx rendered a
    "24h power draw" `AreaChart` built from `Math.random()`-jittered points
    around the latest reading, not from any stored history. Removed
    entirely and replaced with real "current draw" cards sourced from the
    latest `PowerTelemetry`/`CoolingTelemetry` rows — never synthesize a
    time series to fill a chart slot.
12. **Hardcoded "Safe To Migrate" claim** — the consolidation section always
    rendered a green "Safe To Migrate" badge regardless of whether a real
    safe target existed. Fixed by fetching the server's own recommendation
    from `/recommendations` and deriving the badge from its actual
    `impact.safe` / `impact.target_server_id`, matching what
    `_rank_consolidation_candidates()` actually found.
13. **Reports.jsx read two non-existent fields** — `decisionCounts?.dismissed`
    (the real backend key is `rejected`) and `d.recommendation_type` (not a
    field on `OperatorAction`; the actual per-decision target is
    `target_server_id`). Both silently rendered blank/"—" instead of
    erroring, which is why this went unnoticed. Fixed the counts key and
    swapped the dead "Action Type" column for a real "Target" column.
14. **Preferences.jsx `DEFAULT_WEIGHTS.water_weight` was `1.0`** — the actual
    `models.Preferences.water_weight` column default is `0.5`. "Reset
    Defaults" was resetting to a plausible-looking but wrong number. Fixed
    to match the backend default exactly (this is exactly the failure mode
    the comment above `DEFAULT_WEIGHTS` already warned about).
15. **Orphaned duplicate `Recommendation` rows** — `_upsert_flag()` creates a
    *new* `Flag` row (new id) each time a condition re-triggers after having
    previously resolved, so a server flapping idle/healthy/idle repeatedly
    accumulated several `Flag` rows over time, only the newest one active.
    `sync_recommendations()` only ever created/updated recommendations for
    *active* flags — it never cleaned up recommendations tied to the older,
    now-resolved flags, so they piled up as stale duplicates (confirmed
    live: 5 stale pending rows for S4 alone). Fixed with a withdrawal pass:
    any `pending` recommendation whose `flag_id` is no longer in the active
    set gets `status = "withdrawn"`.
16. **What-if consolidation only ever surfaced one candidate** — the original
    `_find_consolidation_target()` picked a single best target internally
    and returned only that one, so an operator had no way to see what else
    was considered or how close the alternatives were. Replaced with
    `_rank_consolidation_candidates()` (see "Phase 2 — what's actually
    built" above), which returns the full ranked list; the what-if response
    now exposes it as `candidates`, and `RecommendationDetail.jsx` renders
    it as a table.
17. **Power model was structurally unusable for What-If, for two stacked
    reasons, not one** — (a) trained on the Kaggle dataset's power scale
    (tens-to-hundreds of kW) vs. live telemetry's single-digit kW, and (b)
    `power_monitor.py`'s `it_power_kw` was pure `random.uniform(1.5, 4.5)`
    with **zero relationship to CPU/memory/anything else** — so even a
    correctly-scaled model would have been applying a real-world learned
    relationship to a live domain that had no such relationship to begin
    with, which is worse than not using the model at all. Fixed both:
    `train_model.py` now rescales the training target
    (`rescale_power_target()`) into the live IT-power range, and
    `power_monitor.py` now generates `it_power_kw` as a real function of
    each server's current CPU (85% weight) and memory (15% weight) plus a
    baseline idle draw, fetched live from `GET /servers` each cycle. With
    both fixed, `calculate_what_if()` now uses the power model as the
    primary basis for the post-move energy estimate (falls back to the old
    CPU-ratio formula only if the model or target cooling telemetry is
    unavailable) — see "Phase 2 — what's actually built" → `recommendations.py`
    above for the full reasoning and the honest limits that remain even
    after this fix.
18. **What-if's safety check only ever looked at a candidate target's
    current snapshot** — a target passing the current-state check could
    still be a bad pick if it was about to get busy on its own, and nothing
    anywhere checked for that. Fixed by adding `forecast_candidate_server()`
    (see "Phase 2" above) and running its prediction through the same
    safety check, in addition to the current-state one — see point 2 under
    `recommendations.py` above.
19. **Running the project via `.claude/launch.json` silently used SQLite
    instead of Postgres** — the "backend" preview config ran
    `uvicorn app.main:app --port 8000 --app-dir backend` with no
    `--env-file`, so `DATABASE_URL` was never loaded and `database.py`
    fell back to its `sqlite:///./greenops.db` default. Telemetry still
    flowed and the dashboard still looked correct (SQLAlchemy abstracts the
    backend away, so nothing *looked* wrong) — it just wasn't writing to
    `greenops_db` in Postgres as documented above. Caught by noticing a
    direct DB query returned data from Sep 4-5 instead of the current
    session. Fixed by adding `"--env-file", "backend/.env"` to that
    config's `runtimeArgs` — note the path is relative to the **project
    root**, not `backend/`, since `--app-dir` only changes Python's module
    search path, not the process's actual working directory (same reason
    the frontend config uses `npm --prefix frontend` instead of a `cwd`
    field — there isn't one). **Always confirm which database a running
    backend is actually using** before trusting anything queried through
    it — check the startup log line ("Loading environment from...") or
    query Postgres directly and compare row timestamps, don't assume.
    **This bit twice in the same session**: right after fixing the backend
    config above, `train_workload_forecast.py` was run from a bare
    `python -m app.train_workload_forecast` in a fresh shell with no
    `DATABASE_URL` set — same fallback, same silent wrong-database problem,
    just via a direct script invocation instead of the launch config. It
    trained a model that looked fine (real metrics, real R²) but was
    learned from stale Sep 4-5 SQLite data, not the live Postgres telemetry
    it would actually be applied to. Caught by checking the saved
    `training_from`/`training_to` timestamps in `forecast_metrics.json`
    against what Postgres actually has, and re-run with
    `DATABASE_URL=postgresql://greenops_user:green123@localhost:5432/greenops_db`
    set explicitly in front of the command. **The lesson generalizes past
    this one config file**: any ad-hoc script or training run that imports
    `app.database.SessionLocal` needs `DATABASE_URL` set in its own shell
    environment — it does not inherit it from `.env` automatically the way
    `uvicorn --env-file` does. Set it explicitly for every such command, not
    just the one that starts the server.

If something looks numerically "off" again, check for the same class of
issue: an assumption about cadence/scale that isn't actually enforced
anywhere in code, or a SUM/aggregate that isn't scoped to "current state
only." If something looks like a previously-fixed bug is back, check
whether the file was edited outside this conversation before assuming a
regression in the assistant's own work — always trust what's actually on
disk over this document, and diff against the description above rather
than assuming it's unchanged.

## How to run it

```bash
# Backend
cd backend
python -m venv venv && source venv/bin/activate      # Windows: venv\Scripts\activate
pip install -r requirements.txt
python -m app.compute_thresholds     # one-time: derive per-type thresholds from the dataset
python -m app.train_model            # one-time: train CPU + power models (~15s)
uvicorn app.main:app --reload        # API at http://localhost:8000

# Simulators (each in its own terminal — all 4 needed for live-updating data)
cd simulators
python server_monitor.py
python power_monitor.py
python cooling_monitor.py
python storage_monitor.py

# Frontend
cd frontend
npm install
npm run dev                          # UI at http://localhost:5173
```

`DATABASE_URL` env var swaps SQLite for Postgres — zero code change,
`database.py` reads it automatically.

## Non-negotiable conventions — don't "fix" these

1. Data provenance stays honest: live = simulated, ML training = real
   dataset. Never blur this in copy.
2. Per-server-type idle thresholds, never a flat global number.
3. CPU model excludes `cpu_utilization` from its own inputs; power model
   includes it. Keep the asymmetry.
4. Model selection favors simplicity — RF/XGBoost need ≥5% relative MAE
   improvement over Linear Regression to be chosen.
5. WUE/cost/carbon are estimates from published/placeholder constants —
   never present as measured.
6. PUE is the only metric trustworthy as a "real" ratio — don't conflate its
   credibility with WUE's.
7. No gauges/rings/progress bars in the UI — verdict pills + plain-English
   relationship text instead.
8. Don't build anything from `docs/ROADMAP.md` (forecasting, what-if engine,
   recommendation ranking, criticality gating, ESG export) without treating
   it as new Phase 2 work — re-read the roadmap section first, it has
   specific algorithms and explicit "honest limitations" already designed in.

## Explaining this project to a reviewer — key talking points

- Lead with the mental model (`OBSERVE → ANALYZE → PREDICT → EVALUATE →
  RECOMMEND`), not the ML — the ML models are a validation layer, the core
  of Phase 1 is the explainable rule engine.
- State the CPU model's R²=0.845 and the power model's R²≈0.42 together,
  unprompted — the gap is a real, honest finding (these signals explain CPU
  well, power less well), not something to average away or hide.
- "Why Linear Regression, not XGBoost?" → the promotion bar (≥5% relative
  MAE) was set before results were seen; nothing cleared it. That's rigor,
  not settling.
- "Why do live predictions sometimes miss by more than your MAE?" → training
  data is real, live data is simulated with its own simpler formula — a
  genuine distribution shift, which is exactly why measured-vs-predicted is
  shown side by side instead of hidden.
- Mention the two bugs caught via end-to-end testing (dummy-variable trap,
  idle-badge window mismatch) as evidence of rigor, not a confession — offline
  metrics alone didn't catch them; live testing did.
- Known, deliberately-unfixed gap: no criticality/SLA/redundancy field exists
  — telemetry can't tell you *why* a server matters, only *how hard* it's
  working. Phase 2's recommendation engine is designed to gate on a declared
  criticality flag before proposing anything.
- State simulated-vs-real data provenance yourself, early, unprompted.
